## Calendar coloring: by current holder, not creator; President gets its own legend color (this session, no schema changes)

User reported real confusion from a live screenshot: a task he'd created and assigned to a department showed as the calendar's gray "Unassigned" color, even though its assignee chain clearly had an active department step. Root cause: `taskCalendarColor()` was always colored by `tasks.creator_department_id` — the department of whoever *created* the task — not who it's currently assigned to. **Follow-up ask, same conversation**: give President-held tasks their own distinct legend color rather than folding them into "Unassigned" (an individual assignee step with no department, which is what a President-assigned task looks like) — "to show hierarchy." Added `PRESIDENT_TASK_COLOR` (`constants.ts`, reuses the exact brand gold hex rather than inventing a new hue) and an `isPresidentTask` check in `taskCalendarColor()` that takes priority over department color (but still loses to the done/blocked/overdue overrides, unchanged). The calendar's dynamic legend row is now sorted President-first, then departments alphabetically, "Unassigned" last, instead of arbitrary query order — a small extra nod to "show hierarchy" beyond just the color.

**Verification**: `tsc`/`eslint`/`npm run build` clean. `task_assignees_select`'s existing RLS policy (`can_view_task(task_id)`) already scopes this new query to the same visibility as the tasks list itself, so no new access-control surface was added.

## Messaging upgraded to instant push (this session, migration 0033)

Follow-up to the lightweight messaging feature above, same night — the user asked what it'd take to make delivery instant instead of polled, chose to build it. Verified the exact Supabase Realtime Authorization/Broadcast-from-Database API against current docs via WebSearch/WebFetch before writing any SQL, rather than relying on training-data recall for an unfamiliar, security-relevant system-schema surface (`realtime.messages`).

**How it works**: an `AFTER INSERT` trigger on `messages` (`broadcast_new_message()`, calling `realtime.send(...)`) broadcasts only `{conversation_id, message_id}` — never message content — over a private channel named `conversation:<id>`. A new RLS policy on `realtime.messages` reuses `is_conversation_participant()`, so only actual participants can even receive the ping (same privacy model as the rest of messaging — no admin bypass). The client subscribes to that channel and, on receiving a ping, calls the existing `fetchMessages` Server Action — the same decrypt-server-side path used everywhere else, just triggered by a push instead of a timer. This was the whole point of designing it this way: message content (encrypted or not) never touches Realtime, so there's nothing new to keep in sync with `src/lib/encryption.ts`.

The old 4s poll is now a 20s fallback safety net (dropped socket, missed event), not the primary delivery path.

**Verification**: `tsc`/`eslint`/`npm run build` clean; trigger and RLS policy both confirmed present live via direct query (not just the CLI's success message); did an actual end-to-end smoke test — inserted a real test message via the Management API inside a transaction that also cleaned up after itself, confirmed the trigger fired with no error. While verifying, found the user had already independently tried the feature live (a real 3-person group conversation with one message) — left it alone, it's genuine usage, not test residue to clean up.

## Lightweight internal messaging (this session, migration 0032)

Client's ask: "its own messaging system inside of it." Scoped down with the user to *lightweight* — DMs and small group chats, an unread badge, tied to the existing people already in the app. Built and shipped same-night per explicit "run it," without a formal plan-mode round-trip (the user was heading to sleep and unavailable to review a plan) — design decisions made directly, same rigor as the rest of this session (verified typecheck/lint/build, confirmed live against the database with `pg_query`/`gen types` before considering it done).

**New tables**: `conversations`, `conversation_participants` (join table, `last_read_at` drives the unread badge), `messages`. RPC-only writes (`create_conversation_rpc`, `send_message_rpc`, `mark_conversation_read_rpc`), matching the established convention — no direct insert/update policies on any of the three tables.

**Deliberately private, a new stance distinct from tasks**: `is_conversation_participant()` has no `is_boss_or_supervisor()` bypass at all — unlike task visibility, Boss/Supervisor get zero special access to conversations they're not part of. Messaging carries the ordinary privacy expectation of a DM/group chat, not something meant to be broadly visible the way task content is.

**No Supabase Realtime — polling instead, and this was a real architectural call, not an oversight**: message bodies are encrypted the same way task titles/comments/announcements already are (`src/lib/encryption.ts`), and the encryption key never reaches the browser. Raw Postgres `postgres_changes` realtime would stream ciphertext directly to a subscribed client with no way to decrypt it. Rather than build server-side broadcast (decrypt server-side, push over a Realtime channel — a real feature in its own right), the thread view polls a Server Action (`fetchMessages`) every 4 seconds while open — same decrypt-on-the-server pattern every other page here already uses, just refreshed periodically instead of pushed instantly. Worth reconsidering if the client wants closer-to-instant delivery later; the polling interval is the whole tradeoff, isolated to one constant in `src/components/messages/message-thread.tsx`.

**Sending marks your own copy as read** (`send_message_rpc` updates the sender's own `last_read_at`, not just the recipients') — without this, your own conversation would show as unread immediately after you post in it.

**Verification status**: `tsc`/`eslint`/`npm run build` clean; migration `0032` confirmed applied and its three tables confirmed present via a direct query, not just the CLI's own success message; `database.types.ts` verified against a real `supabase gen types` post-apply (cosmetic line-wrap diff only). **Not yet done**: any actual manual click-through testing — this shipped without the user available to test it live, same-night. First thing worth doing next session is just opening `/messages` and sending a real message between two accounts.

## Second security review (this session, migrations 0030-0031)

Prompted by how much authorization surface the admin-roles work added — a full inventory of every RLS policy, RPC, storage policy, server action, and page guard, done fresh rather than assumed from memory. Findings, most severe first:

- **Critical, confirmed exploitable**: `tasks_insert`, `announcements_insert`, and `calendar_events_insert` had **no role check at all** live in production — just `created_by`/`author_id = auth.uid()`. Verified directly against `pg_policies`, not migration-file history (their role checks were progressively simplified away during the 0007-0012 "mysterious RLS rejection" saga and never restored once creation moved to RPCs). Same class of bug as the original critical finding in the first security review (`0019`), just on the INSERT side, which never got the same audit. Any Employee could have created tasks, posted company-wide announcements, or scheduled company-wide meetings by calling the Supabase client directly instead of going through the app UI. Fixed in `0030` — dropped all six vestigial insert policies (`task_assignees_insert`/`task_visibility_insert`/`task_attachments_insert` had the same shape of gap at lower severity); confirmed via `pg_policies` post-apply that all six are gone.
- **Low**: three debug functions from the `0009` RLS-debugging saga were still live and callable by any authenticated user, including `debug_try_insert_task` which performs a real INSERT+DELETE against the live `tasks` table. Plus `can_create_task()`, orphaned since `0012`. All four dropped in `0030`, confirmed via `pg_proc` post-apply.
- **Functional regression, not access-control**: `0023` (this session, fixing the to_do/in_progress status bug) rebuilt `create_task_rpc` from a base that predated `0016`'s terminal-step fix, silently reverting the guarantee that a chain's last step can never require confirmation (which would otherwise strand it in `pending_approval` forever — nothing has a "next step" to confirm it). The app's UI (`assignee-chain-editor.tsx`) independently normalizes this before submitting, so it hasn't caused a real stuck task — but the DB is supposed to be the actual guarantee, per this project's own "frontend checks are UX only" principle. Restored in `0031`, confirmed via `pg_proc` post-apply.
- **Clean**: `npm audit` reports 0 vulnerabilities. CSP/security headers unchanged and intact. `.env.local` secrets correctly un-prefixed and gitignored. Every table's write path is now either RPC-only or has an explicit, audited RLS policy — no table has a write policy that's merely vestigial anymore (task-relay + admin-roles + everything else).

**Lesson worth keeping**: the original `0019` cleanup specifically targeted UPDATE/DELETE policies left behind when their writes moved to an RPC. The exact same failure mode existed on the INSERT side the whole time and was never caught, because nobody went back and re-applied that same audit lens to `create_*_rpc` once those existed. Any future RPC migration should explicitly check whether the table's original INSERT policy (not just UPDATE/DELETE) is now vestigial.

## What this is

A task relay/handoff management system built for a real company (ANRI / RCMC BNLMP Management), intended to eventually be sold/delivered to the client. Core model: tasks move through a chain of assignees ("relay") rather than being assigned to one person; role-based dashboards; full audit trail.

**Stack**: Next.js 16.3.0 (App Router, Turbopack, Server Components/Actions), Supabase (Postgres + Auth + Storage), Tailwind CSS v4, FullCalendar v6.1.21.

**Important**: This Next.js version has breaking changes vs. training-data knowledge (`proxy.ts` replaces `middleware.ts`, `next/script` required for inline scripts, etc.). Docs live in `node_modules/next/dist/docs/` — check there before assuming standard Next.js behavior. See `AGENTS.md` at repo root.

## CSP, task type admin UI, generated types (this session)

**Content-Security-Policy**: implemented as a strict, nonce-based policy rather than the `'unsafe-inline'` shortcut, since every page here already reads cookies (`createClient()` → `cookies()`), which forces dynamic rendering anyway — normally nonce-CSP's main cost, but already paid for here regardless. `src/lib/supabase/middleware.ts` generates a fresh nonce per request, sets it as both the `x-nonce` request header and part of the `Content-Security-Policy` response header; the root layout (`src/app/layout.tsx`, now `async`) reads `x-nonce` via `headers()` and passes it to the theme-init `<Script>`. `script-src` is strict (nonce + `'strict-dynamic'`, no `'unsafe-inline'`). `style-src` still needs `'unsafe-inline'` — confirmed by reading FullCalendar's bundled source that it injects a `<style>` tag at runtime with no nonce awareness (`@fullcalendar/core`'s `injectStyles()`); a strict `style-src` would silently break the calendar's base layout. If you ever add a third-party script/library, check whether it also does runtime DOM injection like this before assuming a stricter policy is safe.

**Task type admin UI**: added as a third card on `/accounts` (`TaskTypesManager` component) alongside Allowed Emails and the accounts table — add/delete task types without SQL. Uses the existing `task_types_write` RLS policy directly (not a new RPC): unlike the policies removed in `0019`, this one was already correctly scoped (`is_boss_or_supervisor()` on both `USING` and `WITH CHECK`, no column-tampering risk), so it didn't need hardening.

**Generated TypeScript types**: `src/lib/database.types.ts` is now generated from the live schema (`supabase gen types typescript --project-id dhbjfbdvsybwbbaxmnad`, needs a Supabase **personal access token** — different from the project API keys already in `.env.local`, generate one at supabase.com/dashboard/account/tokens, ideally revoke it after use since it's account-wide) and wired into all three Supabase client factories (`src/lib/supabase/client.ts`, `server.ts`, `service-role.ts`) via the generic type param. **Regenerate this file whenever the schema changes** (new migration adds/changes a table or RPC) — it will drift silently otherwise, defeating the point.

Wiring it in immediately surfaced real mismatches between the hand-maintained `src/lib/types.ts` and the actual schema, all now fixed — useful to know the shape of these if it happens again after a future regeneration:
- **`text` columns constrained only by a CHECK constraint** (`role`, task `status`) generate as plain `string`, not the narrower `Role`/`TaskStatus` union the app uses everywhere. Fixed by narrowing once at the query source (`getCurrentProfile`, `getProfiles`, `getTaskDetail`) rather than at every call site.
- **RPC scalar parameters can't be expressed as nullable** by the generator — Postgres has no "not null" concept for plain function parameters the way it does for columns, so `create_announcement_rpc`'s `p_expires_at` (genuinely nullable — an announcement can have no expiry) still generates as required `string`. Fixed with a small helper, `nullableRpcArg()` in `src/lib/rpc-utils.ts`, used at every RPC call site that legitimately passes `null`.
- **View columns generate as nullable** regardless of the underlying source data's actual nullability (`task_departments.task_id`) — handled with a type-guard filter rather than a blind assertion, so it stays correct if that view's guarantees ever actually change.

## Admin roles & permissions (this session — the biggest single feature so far)

Client's ask: let the President remove users, and add an "Admin Access Level" with self-defined roles/permissions, an audit trail, role assignment history, and two-admin approval for sensitive changes. Full plan (approved via plan mode) saved at the time in `C:\Users\jvanm\.claude\plans\modular-soaring-eclipse.md`.

**Two privilege-escalation bugs caught and fixed during final review, before anything was applied** (worth internalizing as a pattern for any future permission work):
1. `update_account_rpc` initially let anyone with just `manage_accounts` set a profile's plain `role` column to `boss_boss`/`supervisor` — which bypasses `has_permission()` entirely and grants blanket access to *everything*, far beyond what `manage_accounts` was supposed to mean. 2. `remove_user_rpc` had the same shape of gap — a `manage_accounts`-only Admin could remove a President/Supervisor's account. Fixed with the same guard.

Items 1 and 2 were caught by re-reading the SQL logic directly. Item 3 wasn't catchable without actually running it. Reminder for future permission/RLS work in this project: a clean build only proves the TypeScript side — the SQL side needs either a real apply against a throwaway project or very careful manual tracing, since there's no automated migration testing here.

**Removing a user is soft-delete only** (`0028_user_deactivation.sql`, `profiles.deactivated_at`) — reuses the existing email allowlist as the actual sign-in gate (removes their email from `allowed_emails`) rather than a hard `DELETE`, since `tasks.created_by`/`audit_log.actor_id`/etc. all reference `profiles(id)` with no cascade. **Admin activity trail / Role Assignment History** reuses the existing `audit_log` table (`task_id` already nullable) rather than a new one — every new RPC above logs to it with `task_id = null`. Caught and fixed a real exposure while wiring up the read side: the original `audit_log_select`/`audit_log_insert` RLS (`0003_rls.sql`) treated `task_id is null` as "visible/insertable by anyone authenticated," which was harmless when nothing used that branch but would have made all admin activity readable (and forgeable) by any signed-in user once this feature started using it. ## Roles & standing design principles

Roles: `employee` < `department_head` < `boss_boss` / `supervisor` (president-level).

**Boss/Supervisor are visibility-only, never a "final call" override on other people's task work.** This was explicitly corrected by the client/user after an early implementation gave them override power on relay confirmations — reverted in favor of a self-resolve pattern (see `0017_self_resolve_unconfirmable_step.sql`). They *can* block/unblock tasks and moderate announcements (delete, not edit), but cannot confirm/complete someone else's step or edit someone else's content. **Respect this distinction in all future features** — it's a decision the client pushed back hard on once already.

Employees are read-only on task creation / announcements — they can't create tasks, post announcements, or schedule meetings.

## Architecture: the SECURITY DEFINER RPC pattern (important — read this before adding any write path)

Every write in this app (create task, post announcement, relay actions, deletes, etc.) goes through a Postgres `SECURITY DEFINER` PL/pgSQL RPC function, **not** plain RLS `INSERT`/`UPDATE` policies with `WITH CHECK`.

Why: early in the build, RLS `WITH CHECK` policies referencing role/department (e.g. `tasks_insert`, `task_assignees_update`) mysteriously rejected valid writes for every non-`boss_boss` account, despite every individual condition being independently verified true via debug functions. The root cause was never found after extensive isolation testing. The fix was architectural: move authorization logic out of RLS and into RPC functions that do their own `auth.uid()`-based validation in PL/pgSQL, then write as the function owner (bypassing RLS by design).

**If you add a new write path, follow this pattern** — don't reach for a plain RLS-gated insert/update, it has a known history of silently failing for non-president accounts. See migrations `0013`–`0015`, `0018` for the established shape (validate role/ownership in `plpgsql`, `raise exception` on failure, `grant execute ... to authenticated`).

**Exception — Supabase Storage**: file uploads can't go through a Postgres RPC, since the bytes go through Supabase's Storage API rather than PostgREST. Same risk (`storage.objects` and `task_attachments` both had `WITH CHECK (... and can_view_task(...))`, structurally identical to the policies that broke elsewhere, and were never tested against a non-`boss_boss` account). The equivalent fix, applied to the attachment-upload path in `tasks/actions.ts`: a **service-role Supabase client** (`src/lib/supabase/service-role.ts`, using `SUPABASE_SERVICE_ROLE_KEY`) that bypasses RLS entirely, called only after the Server Action has already verified the user is authorized (mirrors the RPC pattern's spirit — authorize in trusted server code, then write with elevated privileges). **This key must never get a `NEXT_PUBLIC_` prefix and must never be sent to the client** — it bypasses all RLS for the whole project. It's in `.env.local` (gitignored, confirmed) but has no production home yet — needs to be added to whatever hosting platform's env vars when this deploys.

## Timezone handling pattern

Any `datetime-local` input must convert to a full ISO timestamp **client-side** before submission — see `src/components/ui/local-datetime-field.tsx`. Parsing a bare `datetime-local` string server-side applies the *server's* timezone, not the user's, which silently breaks the moment client and server run in different zones (e.g. once deployed to Vercel while users are in the Philippines). This component now also supports `defaultValueIso` for pre-filling edit forms (added when building announcement editing).

The History page's date-only filters (`<input type="date">`) intentionally do **not** use this pattern — a few hours of fuzziness at the day boundary was judged an acceptable tradeoff for a history filter, unlike a task deadline. Documented in a comment in `history/page.tsx`.

This has caused real bugs twice already:

## Security review findings (this session) — read before touching auth/RLS

A full manual security review (no GitHub remote exists, so the diff-based `security-review` skill couldn't run against a PR — this was a whole-app manual audit instead) turned up one critical and several other issues, all fixed:

- **Critical — complete privilege escalation**: `profiles_update_self` RLS policy let any authenticated user update their own `profiles` row with no column restriction, including `role`. Since `is_boss_or_supervisor()` and every RPC's authorization check reads `profiles.role` for `auth.uid()`, any employee could grant themselves `boss_boss` with one direct API call, bypassing the Accounts admin page entirely. The policy was never used by any app code (self profile editing was never built) — dropped entirely rather than tightened, in migration `0019`.
- **High — RPC hardening had a gap**: after each write path moved to a `SECURITY DEFINER` RPC (the pattern documented above), the *original* RLS policies those RPCs replaced were never dropped. They remained fully callable directly via the Supabase client SDK with no `WITH CHECK` restricting which columns/values could be written — e.g. `tasks_update` let anyone holding the active step change *any* column on a task directly, not just the status transition the RPC intends; `tasks_delete` let a President delete a task directly without the "must be cancelled first" rule the delete feature is supposed to enforce. Confirmed via grep that no app code depends on any of them (RPCs bypass RLS as the function owner, so dropping the table policy doesn't affect RPC functionality) — all dropped in `0019`: `tasks_update`, `tasks_delete`, `task_assignees_update`, `task_assignees_delete`, `task_visibility_delete`, `task_attachments_delete`, `announcements_delete`, `calendar_events_update`, `calendar_events_delete`.
- **Medium**: no HTTP security headers at all (`next.config.ts` was empty) — added `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Permissions-Policy`. Deliberately did **not** add a Content-Security-Policy — that needs real testing against Google OAuth, Supabase, FullCalendar, and the service worker before shipping, and guessing at one blind risked breaking the app in a way that wouldn't surface until deployed.
- **Medium**: the `task-attachments` Storage bucket had no `file_size_limit` or `allowed_mime_types` (unbounded upload size/type) — added a 25MB cap and a document/image allowlist in migration `0020`.
- **Clean**: no hardcoded secrets, no XSS vectors (React escapes all interpolated text by default; the one `dangerouslySetInnerHTML` is a static string), `npm audit` reports zero vulnerabilities, `friendlyError()` already prevents raw DB errors from reaching the browser, and the `next` param in the OAuth callback isn't an exploitable open redirect (string-concatenated onto `origin`, never URL-parsed).

**Migrations `0019` and `0020` need to be run in Supabase** like every other migration (see the gotcha below) — as of this writing, not yet confirmed run.

## Application-level encryption (this session)

At the client's request, sensitive content is now encrypted **in application code** before it ever reaches Supabase — not via Postgres/`pgcrypto`. This distinction matters: the explicit threat model is "defense in depth if RLS fails again, or if the service role key leaks" — encrypting inside Postgres would mean the key has to be reachable from SQL, which defeats protecting against exactly that second scenario. The key lives only in `ENCRYPTION_KEY` (`.env.local`, 32-byte AES-256 key, base64), server-side only, never sent to the client.

**What's covered**: task titles, task descriptions, task comments, announcement title/body, and attachment file bytes. **What's explicitly not covered** (out of the scope the client chose): calendar event/meeting titles, profile names/emails, task metadata (status, dates, file names/sizes/MIME types — these stay plain since the app needs to query/sort/filter/display them without decrypting, and the client didn't flag them as sensitive).

**Core utility**: `src/lib/encryption.ts` — AES-256-GCM (authenticated; tampering is detected, not silently accepted).
- `encrypt`/`decrypt` (+ `Nullable` variants) for text columns: stored as `"<iv>.<authTag>.<ciphertext>"`, all base64, in the existing `text` column — no schema change needed.
- `encryptBuffer`/`decryptBuffer` for attachment file bytes: raw `[iv][authTag][ciphertext]` layout, since these go straight into Storage rather than a Postgres column.

**Backward compatibility with existing (pre-encryption) data**: `decrypt()` for text fields gracefully falls back to returning the raw value when it isn't in the expected 3-part shape or fails to decrypt — so task/comment/announcement text written before this change keeps displaying correctly, while everything written from now on is encrypted. **Attachments have no such fallback** — there's no reliable way to distinguish "old plaintext file bytes" from "not our format" the way there is for text, so files uploaded before this change will 410 on download with an explanatory message. Given this project currently only has test data, that tradeoff was accepted rather than building a migration path.

**Where encrypt/decrypt happens**: encryption happens once, right before each RPC call in the Server Action (`createTask`, `postAnnouncement`/`updateAnnouncement`, `addComment`, the attachment upload loop in `tasks/actions.ts`). Decryption happens at every read site — `src/lib/queries.ts` (`getTaskList`, `getTaskDetail`), `src/lib/dashboard-queries.ts` (`getRecentlyCompleted`, `getOverdueAndBlockedTasks`, `getUpcomingDeadlines`, `getAnnouncements`), `calendar/page.tsx`, `history/page.tsx`. **If you add a new query that selects `title`/`description`/`body` from `tasks`, `task_comments`, or `announcements`, you must decrypt it there** — nothing enforces this at the type level, it's a manual convention. Everything downstream of these functions (components, other pages) receives already-decrypted plaintext and needs no changes.

**Attachments — architecture change**: file bytes are encrypted before upload (still via the service-role client, same as before). This broke the previous download flow (`createSignedUrl` + direct `<a href>` to Supabase Storage), since that would just hand the browser ciphertext. Replaced with a Route Handler, `src/app/(app)/tasks/[id]/attachments/[attachmentId]/route.ts`, which checks authorization against the `task_attachments` table (respects RLS via `can_view_task`), fetches the encrypted bytes with the service-role client, decrypts, and streams the real file back with the original filename/MIME type (kept as plaintext metadata). The old `getAttachmentUrl` action and signed-URL logic were removed as dead code.

**Gotcha that already bit once — Storage MIME allowlist vs. encryption**: migration `0020` (security review) added a document/image MIME allowlist to the bucket; encryption (added later the same session) made every upload go through as `application/octet-stream` regardless of the real file type, since Storage only ever sees ciphertext now. Every upload failed (`mime type application/octet-stream is not supported`) until `0021` relaxed the bucket to accept `octet-stream`, with the *real* type/size validation moved into application code (`ALLOWED_ATTACHMENT_MIME_TYPES`/`MAX_ATTACHMENT_BYTES` in `tasks/actions.ts`, checked before encryption while the real `file.type` is still visible). **Lesson for future work**: any bucket-level Storage restriction (MIME type, etc.) is checked against what's actually uploaded — once content is encrypted before upload, that's always ciphertext, so this class of restriction has to live in application code instead, checked before encrypting.

## Email allowlist replaces the Workspace domain check (this session)

The client clarified this company has no Google Workspace — employees sign in with personal Gmail-type addresses. The domain check (`auth/callback/route.ts`) is a no-op when `NEXT_PUBLIC_GOOGLE_WORKSPACE_DOMAIN` is blank, which meant **anyone with any Google account could sign in**, and since `profiles_select` RLS is `to authenticated using (true)`, they'd immediately be able to read the full staff directory (every name/email/role/department) — a real PII exposure, not just an unassigned-employee annoyance, discovered while scoping out what "get everyone into the system" actually required.

Fix: `allowed_emails` table (`0022_email_allowlist.sql`), gated entirely behind `SECURITY DEFINER` RPCs (no plain RLS policy on the table at all — matches the established convention). `is_email_allowed(email)` is checked in the OAuth callback alongside the (now effectively unused, but harmless to leave) domain check; anyone not on the list gets signed back out immediately, same as a wrong-domain account. The migration grandfathers in every email that already has a `profiles` row, so existing test accounts (including the President's) aren't locked out. Managed from a new "Allowed emails" card at the top of the Accounts page (`AllowedEmails` component) — boss_boss/supervisor only, add/remove backed by `add_allowed_email_rpc`/`remove_allowed_email_rpc`.

**Operational implication**: before pointing a new person at the sign-in page, their email needs to be added here first — otherwise they'll hit a "not approved yet" error on their first sign-in attempt. Worth being explicit about this in the SOP, since it changes the onboarding order from "let them sign in, then set them up" to "add their email first, then let them sign in."

## Mobile responsiveness + dashboard UI balance (this session)

- **Sidebar**: was a permanently-docked 240px column with no responsive handling — unusable on a phone. Restructured into `src/components/nav/app-shell.tsx` (client component holding open/close state) rendered from the layout; below the `lg` breakpoint the sidebar becomes an off-canvas drawer opened via a hamburger button in `TopBar`, with a backdrop and auto-close on navigation.
- **Calendar**: a full 7-column month grid has no usable width on a phone (event titles truncated to 1-2 characters). `calendar-view.tsx` now imperatively switches to `listWeek` on mount if the viewport is under 640px (FullCalendar's `initialView` prop only applies once, so this can't be done declaratively) — deliberately only on mount, not on every resize, so it doesn't fight a view someone picks manually mid-session. The header toolbar also gets `flex-wrap` under 640px in `globals.css` since three button groups don't fit one row at phone width.
- **Accounts table**: 4 columns don't fit mobile width without truncating role/department to a couple of characters. Now renders two parallel layouts — the table (`hidden md:block`) and a stacked card per person (`md:hidden`) sharing the same state/handlers.
- **History filter form**: fields now take full width on mobile (`w-full sm:w-auto`) instead of an unpredictable content-based width. Note: the native `<select>` dropdown list itself (what you see when tapping "Department") is OS/browser-rendered, not something this app's CSS can restyle — flagged to the client as expected behavior, not a bug, with the option to build a custom dropdown component if it's worth the effort later.
- **Dashboard card balance**: cards in the same grid row weren't equal height (`Card` component didn't stretch to fill its grid cell), which read as inconsistent. First fix (`h-full` on every `Card`) was reverted after the client flagged it looking worse for badly-mismatched pairs (a 2-stat completion-rate card force-stretched to match an 11-department list left huge dead space). The actual fix: don't force mismatched content to match heights at all — `department_health` and `completion_rate` were made full-width rows (`lg:col-span-2` in `dashboard/page.tsx`) instead of being paired 50/50 with something a different natural size. `department-health-grid.tsx` also had truncated department names (`truncate` class cutting off names like "Mine Environmental Protection and Enhancement Department") — switched to a wrapping list instead of a pill grid.

## Known gaps / not yet done

This list drifted badly out of date at one point — several items below (CSP, task-type admin UI, generated DB types, admin roles) were left marked "not done" long after they'd actually shipped, each with its own dedicated section above. Whoever edits this file next: when a gap gets resolved, delete the bullet here immediately rather than leaving it for a later pass — it does not get reliably caught later.

- **`ENCRYPTION_KEY` has no durable backup outside Vercel/`.env.local`** — if lost, every encrypted row (task titles, comments, announcements, messages) becomes permanently unreadable with no recovery path. Explicitly left as-is for now per the client ("stays as we are still developing it") — revisit once the app is closer to a stable, less-actively-changing state, not before.
- **The Supabase personal access token generated for the admin-roles-work backup and database inspection this session was never confirmed revoked.** It's account-wide, not project-scoped — worth checking supabase.com/dashboard/account/tokens.

- **Org chart sub-units unseeded** — blocked on client input, not a code issue.
- **The two-admin approval flow (sensitive admin-role grants) has been built but not yet click-tested end-to-end** with two real distinct logged-in accounts — needs someone to actually play both the requester and the approver. Test steps are in this session's conversation history if picking this up fresh.
- **CSP is enforcing, not report-only** — `Content-Security-Policy` (not `-Report-Only`) has been live since it shipped, has run under every feature built since with no reported breakage, but was never deliberately soak-tested in report-only mode first. Worth keeping in mind if something ever renders oddly with no visible error — check the browser console for CSP violations before assuming it's something else.

## For the SOP itself

Given the above, likely candidates for what the SOP should cover:
- The migration-must-be-manually-run gotcha (highest-value one to formalize — has caused real outages more than once).
- The RPC-over-RLS convention for any new write path, and why — including the Storage exception (service-role client) for the one write path that can't go through a Postgres RPC, and the lesson from this session's security review that the *original* policy behind an RPC must be dropped, not just left inert.
- Handling of secrets specifically (`SUPABASE_SERVICE_ROLE_KEY`, `ENCRYPTION_KEY`): never client-side, never `NEXT_PUBLIC_`, both need a real production home and `ENCRYPTION_KEY` needs a backup plan before ship.
- The Boss/Supervisor visibility-only principle, as a design rule for any future feature review.
- The encryption convention: any new query touching `title`/`description`/`body` on `tasks`/`task_comments`/`announcements` must decrypt at the read site — not enforced by the type system, easy to miss.
